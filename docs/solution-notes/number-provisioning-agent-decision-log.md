# Number Provisioning — Agent Decision Log

> Notion note: same publishing blocker as every other doc in this thread — this workspace has used all its free blocks. NR's own process calls for a Decision Log row alongside each ADR; this file is that log, kept in the repo instead of Notion for the same reason everything else is.

**Scope:** this file tracks *engineering/implementation* decisions — choices made while writing code, not asked about explicitly, where a reasonable alternative existed. It's the audit trail for "why does the code do it this way." Product-level decisions (scope, phasing, provider choice) are tracked separately in [telnyx-twilio-parity-frd.md](telnyx-twilio-parity-frd.md) §16 — this file doesn't duplicate those.

**How to read this:** each row is one decision, the alternative that was rejected and why, and which files it landed in. Newest first. This file gets a new row every time a non-obvious implementation choice is made in this feature — it's not a one-time backfill.

| 2026-09-29 | `ExotelProvider#order` now merges `'id' => parsed.dig('PhoneNumber', 'Sid')` into its return value before returning | Exotel's v2_beta POST to `IncomingPhoneNumbers` wraps the number under a `'PhoneNumber'` key with `'Sid'` as the identifier — the raw `parsed_response` has no top-level `'id'` key, so `provider_order_id_from(response)` always returned `nil`, storing nil in the DB and breaking all subsequent status polls. TelnyxProvider already returns `response.parsed_response['data']` which has a top-level `'id'`; normalizing Exotel's return to the same shape keeps `provider_order_id_from` generic. Bug found by QA agent (2026-09-29). | Overriding `provider_order_id_from` in the controller per provider type (more branching, same goal) | `exotel_provider.rb`, `orders_controller.rb` |
| 2026-09-29 | Added `rescue Provider::RequestError` to `PollOrderStatusJob#perform`, routing through `requeue_or_fail` | A 4xx/5xx from the provider's status endpoint (rate-limit, transient 5xx, number ID not yet provisioned) raised `RequestError` which is not in `NETWORK_ERRORS` and had no rescue clause — Sidekiq caught it as a hard job crash and managed its own retry schedule (~25 retries over 21 days), bypassing `MAX_ATTEMPTS` entirely and leaving the order stuck in `order_placed` with no `provisioning_error`. `requeue_or_fail` is already the correct handler for all retriable errors. Bug found by QA agent (2026-09-29). | Catching per HTTP status code and routing 4xx to immediate fail / 5xx to retry (over-engineering before confirmed provider error taxonomy) | `poll_order_status_job.rb` |
| 2026-09-28 | Removed the explicit `notice`/`alert` render blocks from `number_provisioning/show.html.erb` rather than hiding the layout's global render | The Super Admin layout (`application.html.erb:90`) already renders `<%= render "flashes" -%>` before `yield` — any additional per-page block produces two banners. Root cause modeled on the same latent bug already present in `payment_gateways/show.html.erb` (left untouched, out of scope). Removing from my page is the minimal fix; suppressing the layout's shared render would risk breaking every other Super Admin page | Wrapping the per-page blocks in a guard checking whether the layout already rendered them (fragile, no shared flag exists) | `number_provisioning/show.html.erb` |

Direct URL access still reaches the page today; if that's not acceptable, it's a real, separate follow-up, not an oversight | Also 404/redirecting the route itself when disabled | `SettingsSideMenu.vue` |

| 2026-09-28 | Fixed `providers_param.with_indifferent_access` → plain `providers_param || {}` | `ActionController::Parameters` doesn't have that method at all (`NoMethodError`, caught live testing a save) — it already resolves string/symbol keys interchangeably on its own, matching how `PaymentGatewayRegistry.save!` handles the identical shape | Adding `.to_unsafe_h.with_indifferent_access` instead of just removing the unnecessary call | `provider_config.rb` |
| 2026-09-28 | `ProviderConfig.admin_view` falls back to declared defaults (`default_enabled`/`default_currency`) when `GlobalConfig.get_value` returns nil, instead of showing raw blank/unchecked | Found live: before this fix the page showed Telnyx as *disabled* with an empty currency field, even though the running code's own fail-open default already treats it as enabled with USD — the admin page was lying about the effective state | Leaving it blank until someone saves once (misleading in the meantime) | `provider_config.rb` |
| 2026-09-28 | Consolidated `NumberProvisioning.enabled?`'s flag-key map and fail-open/fail-closed defaults into `ProviderConfig::DEFINITIONS` (single source), instead of two independent hashes | Building the admin page surfaced that `number_provisioning.rb` and the new `provider_config.rb` would otherwise each keep their own copy of "Telnyx defaults true, Exotel defaults false" — a duplication that could silently drift out of sync | Leaving `NumberProvisioning::ENABLED_CONFIG_KEYS`/`DEFAULT_ENABLED_WHEN_UNSET` as they were, duplicated in the new admin service too | `number_provisioning.rb`, `provider_config.rb` |
| 2026-09-28 | Margin is a **percentage, per provider** (not flat, not one global value) | User decision, explicit (via chat) — resolves FRD Open Question 11, unresolved since 2026-09-23 | Flat amount per provider; one shared value for both providers | `provider_config.rb`, `installation_config.yml` |
| 2026-09-28 | Built a bespoke Super Admin controller/view (mirroring `PaymentGatewaysController`/`payment_gateways/show.html.erb`) instead of extending the generic `app_configs` key-value page | User decision, explicit (via chat) — a structured per-provider table (keys + currency + margin together) doesn't fit the generic page's flat list-of-scalars format well; confirmed via research that Super Admin is plain ERB, not the Vue SPA, before writing any code | Extending `SuperAdmin::AppConfigsController#allowed_configs['number_provisioning']` with more flat keys | `number_provisioning_controller.rb`, `number_provisioning/show.html.erb` |
| 2026-09-28 | `compute_margin_cents` stays stubbed at 0, not wired to the new margin config | `order.provider_cost_cents` is never populated anywhere in this codebase (separate "price normalization" gap) — multiplying a real margin % against a nil/0 wholesale cost would produce a fake-looking number, not a real one. | 2026-09-28 | Fixed `error.response.data.message` → also read `.data.error` | `render_could_not_create_error` returns `{ error: message }`, not `{ message: ... }` — found live in-browser: every specific backend error (including the ones added the same session) was silently replaced by a generic fallback string | Leaving it — found by accident during manual verification, not something to leave once seen | `PhoneNumber.vue`, `BuyPhoneNumberModal.vue` |
| 2026-09-28 | Buy-number modal has no in-modal "check status"/polling step, unlike the original wizard | The new dedicated Phone Numbers listing page shows live status per row — polling inside the modal too would be redundant, and the modal's job ends at "order placed" | Porting the wizard's polling step into the modal unchanged | `BuyPhoneNumberModal.vue` |

| 2026-09-28 | Did not extract a shared composable between the old wizard's search/confirm logic and the new modal's (accepted ~100 lines of duplication) | Matches this project's own "prefer minimal code, avoid premature abstraction" convention (CLAUDE.md) — the two flows diverge in what happens after a successful order (redirect vs. close+refresh), so it wasn't purely "same logic, different shell" | Building a `usePhoneNumberPurchase()` composable now | — |
| 2026-09-28 | Modeled the Phone Numbers page after the **Labels** settings section specifically | Simplest existing "list + Add-modal" precedent in the codebase (no separate edit page, one modal, plain hand-rolled table) — closest structural match, confirmed by research before writing any code | Mirroring Macros' pattern instead (has a per-row component, more structure than needed) | `phoneNumbers/*` |
| 2026-09-28 | Provider resolution (`NumberProvisioning.for`) happens *before* any idempotency claim in `create` | A `ProviderDisabledError` raised after claiming the Redis slot would orphan it as "in_progress" for the rest of the TTL — moving resolution first avoids ever claiming a slot for a request that can't proceed | Catching the error inside the claim and releasing the slot afterward | `orders_controller.rb` |
| 2026-09-28 | Idempotency via atomic Redis `SET NX` two-phase claim (claim → create → update to real order id) | Outside-voice review caught that a naive GET-then-SET lets two near-simultaneous requests both pass the check before either writes | Leaving the naive GET-then-SET version (first pass) | `orders_controller.rb` |
| 2026-09-28 | A `failed` order's idempotency slot is reclaimed, not replayed, on retry | Outside-voice review caught that the first version would silently no-op a retry-after-failure for the rest of the 10-minute TTL, since the stale key still pointed at the dead order | Treating any cached order id as a valid replay regardless of status | `orders_controller.rb` |
| 2026-09-28 | Per-provider feature flags with **different** fail-open/fail-closed defaults when config is unseeded (Telnyx → enabled, Exotel → disabled) | Outside-voice review caught that a blanket `nil → false` default would silently disable Telnyx (the one provider that already works) the first time this deploys ahead of `db:seed` | One shared default for both providers | `number_provisioning.rb` |
| 2026-09-28 | Poll job rescues `ProviderDisabledError` and marks the order `failed` | Without this, a flag flipping off mid-poll escapes `perform()` unrescued and becomes a hard Sidekiq job failure instead of a clean order state | Leaving it unrescued (first pass) | `poll_order_status_job.rb` |
| 2026-09-28 | Per-provider feature flags (`NUMBER_PROVISIONING_TELNYX_ENABLED` / `_EXOTEL_ENABLED`), not one shared flag | Telnyx and Exotel have independently different readiness — Exotel needs to stay off pending its unresolved credential model regardless of Telnyx's state. *(Superseded same day — see the row below: credential model is now resolved, flag stays off for other reasons.)* | One `channel_provider_telnyx`-style flag for the whole feature | `installation_config.yml`, `number_provisioning.rb` |
| 2026-09-28 | `requirements_pending` guard: any recognized-but-not-active/failed status routes there, not into a blind retry-then-`failed` | The real per-provider status field/values are still unconfirmed (no captured response) — this stops the poll job from *lying* by mislabeling "needs requirements" as "failed" after 30 retries, without pretending to know the real requirements flow | Guessing at real status values to special-case | `poll_order_status_job.rb` |
| 2026-09-28 | "Check status" gives up with a different message after 5 attempts | Channel/Inbox creation (what the button is actually polling for) is a known, separately-deferred gap — an order can reach `active` with zero errors and this would otherwise loop "still processing" forever with no indication anything's wrong | Leaving it as an infinite loop | `PhoneNumber.vue` |
| 2026-09-28 | Typed `RequestError` carries the raw HTTP status + body rather than a guessed exception hierarchy per error type | No real captured Telnyx/Exotel error responses exist to design a taxonomy against — giving callers the raw status to branch on is honest about what's actually known | Inventing subclasses like `NotFoundError`/`ConflictError` from assumption | `provider.rb` |
| 2026-09-28 | Explicit `PROVIDER_TYPE` constant per adapter, not derived via `class.name.demodulize` reflection | Reflection silently changes what's written to a DB column a unique index depends on, the moment either class is renamed | Keeping the reflection-based derivation | `telnyx_provider.rb`, `exotel_provider.rb`, `orders_controller.rb` |
| 2026-09-28 | Used `Redis::Alfred` wrapper, not raw `$alfred` | Matches this project's own rubocop `Style/GlobalVars` convention — only `lib/redis/alfred.rb` and a few initializers are exempted from that cop, application code goes through the wrapper | Raw `$alfred.with { ... }` (first pass, caught by rubocop) | `orders_controller.rb` |

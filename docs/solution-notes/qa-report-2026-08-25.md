## Issues found

### ISSUE-001 — Font preload 404 on every page load
- **Severity:** Medium
- **Where:** `app/views/layouts/vueapp.html.erb:31`
- **Detail:** `<link rel="preload" href="/vite/assets/GeistVariable.woff2">` hardcoded a stale production-style path. Vite serves this font from a fingerprinted/dev-proxied path, so the literal href never resolves — 404 on every single page load, plus a follow-on browser warning ("preloaded but not used").
- **Fix:** Use the `vite_asset_path` Vite Ruby helper to generate the correct path for both dev and prod: `vite_asset_path 'shared/assets/fonts/Geist/GeistVariable.woff2'`.
- **Status:** ✅ Fixed and verified (404 gone after reload, confirmed via Resource Timing API).

### ISSUE-002 — `rack-mini-profiler` 500 on every page load (dev-only)
- **Severity:** Low (dev tooling only, not user-facing)
- **Where:** gem dependency — `rack-mini-profiler` 3.2.0 calls `Rack::File`, which Rack 3 renamed to `Rack::Files`. Confirmed via direct curl to `/mini-profiler-resources/includes.js` → `NameError: uninitialized constant Rack::File`.
- **Fix:** Requires bumping `rack-mini-profiler` in the Gemfile — a dependency change, not a UI fix, and out of scope for this pass without confirmation.
- **Status:** ⏭️ Deferred — flagging for a separate task, not fixing here.

### Note — `[Vue Router warn]: No match found for location with path "/"` on every load
- Logged on every boot, before the app redirects to `/app/accounts/:id/dashboard`. Cosmetic/console-only (app functions correctly), likely pre-existing upstream Chatwoot routing behavior, not something introduced by this branch. Not fixing — flagging for awareness only.

### Note — title flickers to a different account name ("DakshAI") momentarily on root navigation
- Observed the browser tab title briefly show a different account's installation name before settling. Needs a dedicated repro pass (multi-account/global-config caching) — flagging, not chasing further in this pass to stay within UI scope.

### ISSUE-003 — Companies pagination footer never pluralizes
- **Severity:** Low (cosmetic/i18n)
- **Where:** `app/javascript/dashboard/components-next/Companies/CompaniesTable.vue:175`
- **Detail:** `t('COMPANIES_LAYOUT.PAGINATION_FOOTER.SHOWING', {...})` was called without vue-i18n's plural-count argument, so the `"... company | ... companies"` pipe form always fell back to singular — showed "Showing 1 to 25 of 26 company" regardless of count. Every other table (Contacts) goes through the shared `PaginationFooter.vue`, which already passes `Number(totalItems)` as the third arg; Companies has its own inline `t()` call that skipped it.
- **Fix:** Pass `Number(totalItems)` as the third argument to `t()`, matching `PaginationFooter.vue`'s pattern.
- **Status:** ✅ Fixed and verified ("Showing 1 to 25 of 26 companies" confirmed live).

### Investigated (not a bug) — Live Chat Campaigns page appeared to show real data + empty state at once
- Text extraction showed 4 campaign cards AND "No Live Chat Campaigns Are Available" simultaneously. Traced via Vue internals: the 4 cards are `ONGOING_CAMPAIGN_EMPTY_STATE_CONTENT` sample/placeholder cards rendered as a faded background illustration (`opacity-30`, `pointer-events-none`, `aria-hidden="true"`) behind the real empty-state message in `EmptyStateLayout.vue` — a deliberate "here's what it looks like" onboarding pattern. The account genuinely has 0 live chat campaigns (verified via component `setupState`). No code change made.

### ISSUE-004 — Super Admin tab title shows "Chatwoot" instead of "NewRelay" (deferred)
- **Severity:** Low, dev-only
- **Where:** Third-party Chatwoot support-widget SDK (`app/views/super_admin/application/_javascript.html.erb`), embedded so super-admins can contact Chatwoot's own support team.
- **Detail:** `application_title` helper correctly returns `'NewRelay'` (verified in code and after a full backend restart — ruled out server staleness). The support widget SDK mutates `document.title` after load, and in local dev `ChatwootHub.support_config` has no real token (confirmed via a `/widget?website_token=` 404), so the widget falls back to showing its own "Chatwoot" branding in the tab title.
- **Fix:** Not a code bug in this app — it's third-party vendor behavior that only surfaces because dev lacks real `ChatwootHub` connectivity. Not fixing here.
- **Status:** ⏭️ Deferred — flagging for awareness, likely non-issue in production with real Hub config.
